[7] DEFENSIVE RECOMMENDATIONS
----------------------------------------------------------------------------------------------------
  1. Disable SSH password authentication (PasswordAuthentication no); use keys + MFA.
  2. Never ship default credentials - 73.9% of attempts here used them. Force a password change on
     first boot for IoT/embedded devices.
  3. Block or rename 'root' logins (PermitRootLogin no) - it was the #1 target.
  4. Rate-limit and auto-ban repeat offenders (fail2ban / sshguard; e.g. 5 failures -> 1 h ban).
  5. Disable TCP forwarding for untrusted users (AllowTcpForwarding no) to stop proxy/spam abuse.
  6. Egress-filter outbound SMTP (25/465/587) from servers that do not send mail.
  7. Feed the IOC list below into firewall / proxy / EDR blocklists and hunt for the file hashes.
  8. Alert on post-login discovery + history wiping (uname, unset HISTFILE) - strong intrusion
     signals.

METHODOLOGY
----------------------------------------------------------------------------------------------------
  Brute force  : >= 10 distinct credential pairs AND (>= 100 attempts,
                 or >= 20 attempts at >= 5/min).
  IoT botnet   : >= 5 attempts, >= 50% of them known default credential pairs.
  Proxy abuse  : any cowrie.direct-tcpip.request (attacker tunnels traffic through the honeypot).
  Dropper      : a file download or wget/curl/tftp command after login.
  Persistence  : writes ~/.ssh/authorized_keys or cron entries after login.
  Risk score   : volume (<=25) + brute 15 + botnet 10 + post-auth activity 20 + tunnel 15
                 + SMTP 5 + commands 10 + download 40 + anti-forensics 5
                 + persistence 25, capped at 100.
                 >=70 CRITICAL, >=50 HIGH, >=30 MEDIUM, else LOW.
  Note         : a honeypot 'accepts' logins on purpose; 'OK' means the attacker got a fake shell.
  (*) T1583.006 is the closest ATT&CK fit for spam relaying; no exact technique exists.
